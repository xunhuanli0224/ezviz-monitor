§一分钟版：完整命令序列

如果你只想复制粘贴，用这一段。假设项目已有代码、GitHub 上还没有仓库。

# 0. 装 GitHub CLI（只装一次，装完重开终端）
winget install --id GitHub.cli -e

# 1. 登录（浏览器设备码授权，只需一次）
gh auth login --web --git-protocol ssh

# 2. 进项目目录，初始化
cd 你的项目目录
git init -b main
git config user.name  "你的名字"
git config user.email "你的邮箱"

# 3. 先写忽略规则，再校验，最后才 add（顺序很重要）
printf 'config.json\nreports/\n__pycache__/\n*.pyc\ndist/\ndist_exe/\n' > .gitignore
git check-ignore -v config.json

# 4. 暂存并人工复核清单
git add -A
git status --short

# 5. 提交
git commit -m "feat: 初始提交"

# 6. 建仓 + 加远端 + 推送，一条命令搞定
gh repo create 仓库名 --public --source=. --remote=origin --push
核心就三件事：本地仓库先行（init → commit）、忽略规则先行（check-ignore 验证）、远端创建交给 gh。 顺序一旦颠倒，最容易出的问题就是把含密钥的文件推进公开仓库。

2六个阶段逐条拆解

每步都给出：为什么做、敲什么、实际输出长什么样、出错了往哪看。

  1. 环境核对
    先确认工具链齐不齐，避免走到一半才发现缺东西
    $ git --version
git version 2.55.0.windows.3

$ gh --version
gh: command not found        ← 未安装，需要装

$ ssh -T git@github.com
Hi xunhuanli0224! You've successfully authenticated, but GitHub
does not provide shell access.          ← SSH 通道本来就是通的

    这一步的结论很关键：SSH 已通，只缺创建仓库所需的 API 授权。推送（push）走 SSH，建仓走 API，是两条不同的通道，别混为一谈。

  2. 初始化与身份
    决定默认分支名，并让提交记录显示正确的作者
    $ git init -b main
Initialized empty Git repository in D:/…/ezviz_monitor/.git/

$ git config user.name  "xunhuanli0224"   # 只对本仓库生效
$ git config user.email "xunhuanli0224@163.com"
    为什么用 -b main：git 2.28 起支持指定初始分支名。不写的话，取决于 init.defaultBranch 配置， 老环境会得到 master，与 GitHub 默认的 main 不一致，后续要额外改名。
    为什么要单独配身份：本机全局 user.name 是占位符「homing你的名字」，直接提交会在 GitHub 上显示成这个名字。 这里用 git config（不带 --global）只改当前仓库，不动你的全局配置。
  3. 忽略规则与暂存（最容易出事的一步）
    确保密钥、二进制、历史报告不会进仓库
    # ① 先写忽略规则
$ cat .gitignore
config.json      ← 含 AppSecret
reports/         ← 本机历史报告
__pycache__/  *.pyc  dist/  dist_exe/  build/  *.spec

# ② 验证规则真的生效（不要只靠眼睛看文件内容）
$ git check-ignore -v config.json reports dist dist_exe
.gitignore:1:config.json      config.json
.gitignore:2:reports/         reports
.gitignore:5:dist/            dist
.gitignore:6:dist_exe/        dist_exe

# ③ 再暂存，并人工复核清单
$ git add -A
$ git status --short
A  .gitignore
A  README.md
A  server.py
A  start.sh
A  web/app.js
…（共 12 个文件，没有 config.json）

    这里踩到的坑：换行符

    git add 时出现一堆警告：

    warning: in the working copy of 'start.sh', LF will be replaced by CRLF
the next time Git touches it

    含义是：Windows 上 core.autocrlf 默认开启，别人克隆时 start.sh 会变成 CRLF 换行， 在 macOS / Linux 上执行会直接报 /bin/bash^M: bad interpreter。补一个 .gitattributes 解决，然后重新归一：

    # .gitattributes
* text=auto
*.sh  text eol=lf
*.bat text eol=crlf
web/vendor/*.js -text      # 压缩库按二进制处理，别改写

$ git add .gitattributes
$ git add --renormalize .        # 按新规则重新计算换行

# 验证存档里到底是 LF 还是 CRLF
$ git show :start.sh | grep -q $'\r' && echo CRLF || echo LF
LF                                ← 正确
    为什么要 git add --renormalize：.gitattributes 只影响后续操作，已经暂存的内容不会自动按新规则重算。
  4. 提交
    本地形成第一个可推送的快照
    $ git commit -F - <<'EOF'
feat: 萤石云多路监控墙（本地代理 + HLS 多开播放 + 失败报告）

浏览器无法直连萤石开放平台（无 CORS、会暴露 AppSecret）…
EOF
 13 files changed, 4060 insertions(+)

    用 -F - 从标准输入读多行提交信息，比堆一串 -m 清爽。提交信息建议写「为什么这么做」，而不是「改了哪些文件」——前者三个月后还有价值。

  5. 建仓与授权
    这一步必须有 API 凭证，SSH 密钥不能用来建仓库

    先装工具并登录：

    $ winget install --id GitHub.cli -e
已成功安装  gh 2.104.0

$ gh auth login --web --git-protocol ssh --skip-ssh-key
! One-time code (7D23-C8D8) copied to clipboard
Open this URL to continue in your web browser: https://github.com/login/device
# 浏览器打开上面地址、粘贴代码、点 Authorize
✓ Authentication complete.
✓ Logged in as xunhuanli0224

    然后一条命令完成建仓、设远端、推送：

    $ gh repo create ezviz-monitor --public --source=. --remote=origin --push
https://github.com/xunhuanli0224/ezviz-monitor
To github.com:xunhuanli0224/ezviz-monitor.git
 * [new branch]      HEAD -> main
branch 'main' set up to track 'origin/main'.
    参数作用
    --source=.以当前目录的本地仓库为源，自动读取提交历史
    --remote=origin顺手把远端命名为 origin，省掉 git remote add
    --push建完立即推送，省掉 git push -u
    --public公开；反之 --private
    关于设备码授权：gh auth login --web 常被认为必须有交互终端。 实测把标准输入重定向到 /dev/null、后台运行时它依然工作——一次性代码会写进输出，gh 自己轮询等待你在浏览器确认。 全程不需要手工输入任何东西，凭证由系统 keyring 保管（本次 token 权限：gist、read:org、repo）。
  6. 推送后验证
    不要相信「推送成功」的提示，要看远端到底有什么
    # 列远端文件清单
$ gh api repos/xunhuanli0224/ezviz-monitor/git/trees/main?recursive=1 \
    --jq '.tree[] | "\(.size // 0)\t\(.path)"'

# 逐个确认敏感文件不存在（返回 404 才算安全）
$ for f in config.json dist_exe/EzvizWall.exe reports; do
    gh api "repos/xunhuanli0224/ezviz-monitor/contents/$f" >/dev/null 2>&1 \
      && echo "$f 存在！" || echo "$f 未推送 OK"
  done
config.json          未推送 OK
dist_exe/EzvizWall.exe 未推送 OK
reports              未推送 OK

$ git status --porcelain | wc -l
0                      ← 工作区干净，无遗漏

3三种建仓方式怎么选

它们的区别只在「谁去调 GitHub 的创建接口」，推送环节都是同一条路。

方式需要什么命令 / 操作适用场景
gh CLI本次采用 安装 gh + 一次浏览器授权 gh repo create 名字 --public --source=. --remote=origin --push 本机开发，后续还要频繁开 issue / PR；一条命令到底
网页建空仓 + SSH 什么都不用装 网页 New repository（不要勾 README / .gitignore）→
git remote add origin git@github.com:用户名/仓库名.git
git push -u origin main		 不想装工具，或给别人演示；零密钥外泄
PAT + REST API Personal Access Token curl -H "Authorization: Bearer $TOKEN" \
-d '{"name":"仓库名","private":false}' \
https://api.github.com/user/repos		 脚本化 / CI 里建仓；token 要妥善保管，用完即删
网页建仓时最容易出的错：勾了「Add a README file」或「Add .gitignore」。 这会在远端产生一个提交，你本地又有独立历史，推送时被拒： ! [rejected] main -> main (fetch first)。 补救是 git pull --rebase origin main 后再推，或者干脆建空仓。

4四个值得记住的判断

① SSH 通了不等于能建仓库

SSH 密钥只解决「推送时的身份认证」，创建仓库是 GitHub 的 REST API，需要 token 或 OAuth。 本次 ssh -T 早就通了，却依然卡在建仓这一步，就是这个原因。

② 忽略规则要「验证」而不是「写好」

.gitignore 对已跟踪的文件无效。如果某个文件曾经被 git add 过， 之后再加进 .gitignore 也没用，必须 git rm --cached 文件 取消跟踪。 所以每次 add 之后都用 git status --short 过一遍清单，比事后补救便宜得多。

③ 换行符是跨平台项目的隐形炸弹

Windows 上不影响运行，但克隆到 Linux 后 .sh 会带着 \r，解释器找不到 /bin/bash\r。 加 .gitattributes 是根治手段；只在自己的机器上测试永远发现不了这个问题。

④ 提交作者身份分三层，优先级从高到低

层级配置命令影响范围
仓库级git config user.name "…"仅当前仓库（本次采用）
全局级git config --global user.name "…"当前用户所有仓库
系统级git config --system user.name "…"整台机器

5报错对照表

报错信息原因处理
gh: command not found 未安装，或装完没重开终端 装好后重开终端；或直接用全路径 "C:\Program Files\GitHub CLI\gh.exe"
Permission denied (publickey) 本机公钥没加到 GitHub ssh -T git@github.com 确认；不通用 gh auth login 或手动加 ~/.ssh/id_ed25519.pub
! [rejected] main -> main (fetch first) 远端已有提交（网页建仓勾了 README） git pull --rebase origin main 后重新 push
fatal: remote origin already exists 重复添加远端 git remote set-url origin 新地址
src refspec main does not match any 还没有任何提交就 push 先 git add -A && git commit -m "init"
Support for password authentication was removed 用 HTTPS 加账号密码 改走 SSH，或用 PAT 当密码
bad interpreter: /bin/bash^M 仓库里 .sh 被存成 CRLF 加 .gitattributes（*.sh eol=lf）+ git add --renormalize .
HTTP 401: Bad credentials gh 的 token 失效或被撤销 gh auth login 重新授权，gh auth status 查状态

6已经推错了怎么补救

最需要警惕的情形：密钥 / 密码 / Token 被推送上去。 删除文件再提交一次是不够的——它仍然留在历史提交里，任何人克隆都能翻出来。
情形补救方式是否彻底
提交了但还没 push git reset --soft HEAD~1（保留改动）或 git reset --hard HEAD~1（丢弃改动） 是
已 push，文件不该进仓库但无敏感信息 git rm --cached 文件 → commit → push 否，历史里仍在
已 push，且含密钥 ① 立刻作废该密钥 / Token（这一步最重要）
② 再用 git filter-repo 或 BFG 改写历史并强推
③ 通知协作者重新克隆		 是，但必须换密钥
仓库误建为公开 gh repo edit --visibility private --accept-visibility-change-consequences 是
顺序原则：先止血（作废凭证），再清理历史。反过来做，凭证在你清理的这几分钟里就是公开可用的。

7之后的日常操作

仓库建成后就不需要 gh 了，日常只有三行命令。

$ git status                              # 看改了什么，先看再动
$ git add -A && git commit -m "fix: 说明修了什么"
$ git push                              # 凭证由 gh 存在 keyring，不必再登录
想做的事命令
改仓库可见性gh repo edit --visibility private
加标签gh repo edit --add-topic 标签名
看远端状态gh repo view --json name,visibility,url
查看登录账号gh auth status
换账号gh auth logout 后重新 gh auth login
删除仓库gh repo delete 用户名/仓库名 --yes（不可恢复）
关于密钥存放：config.json 里是明文 AppSecret，已被 .gitignore 排除。 但只要你手工把目录拷给别人，它就是跟着走的——分发包请用 portable.py（默认剔除凭证）。
